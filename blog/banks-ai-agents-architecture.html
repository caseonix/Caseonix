Agentic AI & Banking

Banks told AI agents to stay out. Here is the architecture that lets them back in.

The block is correct. The cause is not the agent. It is an access model where agents log in with the customer’s password.

By Srivatsa Kasagar · October 30, 2026 · 10 min read
Share: LinkedIn X

TLDR: In October 2026, JPMorgan and Schwab started to block outside AI agents from customer accounts. The block is correct. The cause is not the agent. The cause is the access model: agents log in with the customer’s password. Banks need an agent gateway. The gateway gives each agent its own identity, a scoped and revocable consent, and an audit trail. Canada has a head start because its new open banking law already bans screen scraping.

What happened

Two weeks changed the agent conversation in banking.

  • On October 13, JPMorgan CEO Jamie Dimon said on the Q3 earnings call that the bank will not let outside agents into its systems.
  • Dimon told customers that a “liability transfer” occurs when they give an agent access. (Source: CNBC, Banking Dive.)
  • JPMorgan blocks external agents even when a connector such as Plaid holds the customer’s login. (Source: ValueAdd VC, citing a JPMorgan spokesperson.)
  • On October 16, Schwab CEO Rick Wurster told Bloomberg TV that Schwab blocks dozens of agent login attempts each week.
  • Meta’s Muse is the most visible target. Meta launched it in September as a personal agent for email, travel, and calendars. Its finance features connect through Plaid.
  • Amazon blocked Muse from its retail site in September.

The banks are not against agents. JPMorgan runs agents internally. It also pilots its own cash tool, Smart Cash, which forecasts cash flow and moves funds for yield. That is the same job an outside agent wants to do.

So read the block correctly. Banks are saying two things at once:

  • “Your agent is a security risk.”
  • “We want to own the agent layer.”

Both statements are true. The first one has an engineering fix. The second one is a business decision that the fix makes harder to defend.

Why credential sharing fails

Today, most personal agents reach a bank account in one way. The customer gives the agent a username and password. The agent then logs in as the customer.

flowchart LR
    C["Customer"] -- "Gives username + password" --> A["Personal AI agent"]
    A -- "Logs in as the customer" --> B["Bank login"]
    B --> S["Full account session<br/>(read + move money)"]
    B -. "Cannot tell agent from human" .-> X["Bank risk + fraud controls"]

This model has four problems. Each one is a design problem, not an AI problem.

  • No identity. The bank sees the customer. It cannot see the agent. It cannot tell Muse from a fraudster who holds the same password.
  • No scope. A password unlocks everything. The customer may want “read my balance.” The password gives “move all my money.”
  • No clean revocation. To remove the agent, the customer must change the password. That breaks every other tool that uses it.
  • No attribution. When a wrong transfer occurs, the log says “customer.” Nobody can prove which party acted.

Dimon’s “rogue agents” worry follows directly from these four gaps. A bank that cannot identify, limit, or attribute an actor must block it. I would block it too.

The target architecture: an agent gateway

The fix is not a better agent. The fix is a new front door at the bank. I call it the agent gateway.

The rule is simple. An agent never holds the customer’s credentials. It holds a token that the customer granted to that agent, for named actions, for a limited time.

flowchart TB
    subgraph Customer side
        C["Customer"]
        A["Personal AI agent<br/>(registered identity + signing key)"]
    end

    subgraph Bank agent gateway
        R["Agent registry<br/>who the agent is, who built it, its status"]
        CS["Consent service<br/>scopes, limits, expiry, revoke"]
        P["Policy engine<br/>value caps, velocity, risk score"]
        SU["Step-up approval<br/>customer confirms in bank app"]
        L["Audit log<br/>agent ID + consent ID on every call"]
    end

    subgraph Bank systems
        RO["Read APIs<br/>balances, transactions"]
        WR["Write APIs<br/>transfers, payments"]
        K["Kill switch<br/>per agent, per customer, global"]
    end

    C -- "Grants consent in bank app" --> CS
    CS -- "Issues scoped token" --> A
    A -- "Signed request + token" --> R
    R --> CS --> P
    P -- "Low risk, in scope" --> RO
    P -- "Money movement or over limit" --> SU
    SU -- "Customer approves" --> WR
    P --> L
    SU --> L
    K -.-> R

Each component has one job.

  • Agent registry. Each agent product registers with the bank. It gets an ID and a signing key. The bank knows the vendor and can suspend the product.
  • Consent service. The customer grants consent inside the bank’s own app. The customer picks the scopes. Consent has an expiry date. The customer can revoke one agent and keep the others.
  • Policy engine. The bank sets limits per scope. Examples: a cap per transfer, a cap per day, approved payees only. The bank, not the agent vendor, owns these rules.
  • Step-up approval. Any action that moves money above a limit goes back to the customer. The customer confirms in the bank app. The agent cannot approve its own action.
  • Audit log. Every call carries the agent ID and the consent ID. This record is what makes liability workable.
  • Kill switch. The bank can stop one agent for one customer, one agent product for all customers, or all agents.

Nothing here is new technology. OAuth 2.0 scopes, signed requests, and step-up authentication already exist. Open banking regimes already use most of them. The new part is to treat the agent as a first-class party with its own identity, rather than as a disguised customer.

How one request flows

Here is a common case. The agent sees a high balance in chequing. It wants to move money to a higher-yield savings account. This is the exact case that worries banks about deposit flight.

sequenceDiagram
    autonumber
    participant Cu as Customer
    participant Ag as AI agent
    participant GW as Agent gateway
    participant Po as Policy engine
    participant App as Bank app
    participant Core as Core banking

    Cu->>App: Grant agent "read balances" + "transfer between own accounts"
    App->>Ag: Scoped token (expiry set)
    Ag->>GW: Read balances (signed, with token)
    GW->>Po: Check scope + risk
    Po-->>GW: Allow
    GW->>Core: Get balances
    Core-->>Ag: Balances
    Ag->>GW: Transfer to savings (signed, with token)
    GW->>Po: Check scope, amount, velocity
    Po-->>GW: Over limit, step-up needed
    GW->>App: Ask customer to approve
    App->>Cu: Approve transfer?
    Cu->>App: Approve
    App->>GW: Approved
    GW->>Core: Execute transfer
    GW->>GW: Log agent ID, consent ID, approval ID
    Core-->>Ag: Confirmation

Note what the bank keeps in this flow:

  • The customer relationship. Consent and approval happen in the bank’s app.
  • The risk decision. The policy engine is the bank’s.
  • The evidence. The audit log answers “who did what, under which consent.”

Note what the bank gives up: the ability to stop a customer from moving their own money to a better rate. I think banks should give that up. A bank that blocks agents to protect low-yield deposits will lose that argument with regulators and with customers.

Liability: who pays when the agent is wrong

Dimon is right that liability is the real question. Who pays for a wrong transfer is still unsettled in the US. (Source: Trending Topics, Crypto Briefing.)

The gateway makes a fair answer possible because it produces evidence. Here is the split I propose:

  • The customer pays when the customer shared credentials outside the gateway. This is Dimon’s position, and it is fair for that case only.
  • The agent vendor pays when the agent acted outside the granted scope, or misread the customer’s instruction within it.
  • The bank pays when its policy engine approved an action that its own rules should have stopped.

Without a gateway, every case collapses into the first line. The customer carries all the risk because nobody can prove otherwise. That outcome is bad for customers and bad for adoption.

The Canadian angle

Canada is in a better position than the US on this. Two pieces of law are already in motion.

Consumer-Driven Banking (open banking)

  • Bill C-15 received Royal Assent on March 26, 2026. It completes the framework and explicitly bans screen scraping. (Source: Facephi, Bank of Canada remarks via Open Banking Expo.)
  • The Department of Finance published the proposed regulations on June 27, 2026. The Bank of Canada supervises the framework. (Source: Canada Gazette, Bennett Jones.)
  • The framework sets a statutory liability structure between participants. (Source: Open Banking Expo, on Finance Canada’s framework.)
  • Rollout is phased. Read access comes first. Write access, such as payment initiation, comes later. Final go-live dates were still not confirmed. (Source: Fiskil.)

The open question: does an AI agent that logs in with a customer’s password count as screen scraping under C-15? I do not know. I think it should. If the answer is yes, every credential-sharing agent is out of bounds in Canada, and the accredited API path becomes the only legal path. That is the gateway model, written into law.

OSFI Guideline E-23

  • E-23 takes effect on May 1, 2027. It brings AI and machine learning models into model risk management at federally regulated financial institutions. (Source: BLG, Mondaq.)
  • This applies to the bank’s own agents, not to the customer’s agent.
  • So the bank’s own cash-sweep agent needs an inventory entry, a risk rating, validation, and monitoring. An outside agent that enters through the gateway does not. The gateway’s policy engine is what the bank governs.

That split is useful. The gateway lets a Canadian bank say: “We govern our models under E-23. We govern outside agents through consent and policy at the door.”

What to build first

Do not try to build everything. Start with read access, the same order that Canada’s open banking rollout uses.

  1. Build the agent registry. Give each agent product an ID and a key.
  2. Add consent in the bank app. Start with read-only scopes.
  3. Log the agent ID and consent ID on every call.
  4. Add the kill switch.
  5. Add write scopes for transfers between the customer’s own accounts.
  6. Add step-up approval for any money movement over a limit.
  7. Add payments to outside payees last.

Steps 1 to 4 carry low risk and give the bank visibility on day one. Steps 5 to 7 need the liability model agreed first.

On the vendor side, Meta and Sierra are working on a protocol that lets personal agents identify themselves and get customer permission. (Source: Trending Topics, ValueAdd VC.) Banks should engage with that work now. If banks do not shape the agent identity standard, the agent vendors will shape it alone.

My position

The block is the correct short-term move. A bank cannot let an unidentified actor with full credentials move money.

The block is the wrong long-term strategy. Customers will use agents. The only choice a bank has is whether those agents come through a door the bank controls, or through a password the bank cannot see.

Build the door.
