Making six models look like one: a multi-agent orchestration pattern

Six model calls in three phases, streaming the whole time — and the orchestration that makes them read like one calm assistant thinking out loud.

By Srivatsa Kasagar · May 14, 2026 · 8 min read
Share: LinkedIn X

When a Consul user asks for a portfolio briefing, they click one button and watch a document assemble over about thirty seconds: risk appears, then tax, then fees, then a synthesized "Bottom Line" streams in at the top. It reads like one assistant thinking out loud.

It's six model calls in three phases, streaming their own progress the whole time. Here's the pattern that makes them look like one.

Why six instead of one

A good briefing isn't one prompt. What a risk officer asks ("how concentrated is this, what's the drawdown") has nothing to do with what a tax strategist asks ("any harvest candidates, is this in the wrong account"). Put it all in one mega-prompt and you get shallow, hedged output that's good at nothing.

So we model it like a real advisory team: narrow specialists do deep passes, then a chief of staff assembles their findings. Five specialists, one synthesizer. That creates a dependency graph, not a list:

Four nodes in parallel, one that waits on all four, one that waits on everything.

One request, one stream

The whole pipeline runs inside a single request and returns a ReadableStream as a Server-Sent Events response. No queue, no polling, no background job. runBriefingPipeline returns a stream whose start(controller) function is the pipeline: it calls models, writes to the database, and pushes SSE frames through one helper.

function emit(type: string, payload = {}) {
  controller.enqueue(enc.encode(`data: ${JSON.stringify({ type, ...payload })}\n\n`));
}

Every moment becomes an event: specialist.started, specialist.completed, synthesis.delta, briefing.completed. The browser speaks our protocol and never knows how many models ran.

Phase 1: fan out, persist as you go

The four independent specialists run together with Promise.all. Each one writes a running row to the database the instant it starts, then patches it to complete or failed:

await deps.persist.insertSpecialist({ id, briefingId, role, status: 'running' });
emit('specialist.started', { role });
try {
  const { output } = await deps.runSpecialist({ role, model: MODEL, userMessage: prompt, maxTokens: 2000 }, env);
  await deps.persist.updateSpecialist(id, { status: 'complete', output });
  emit('specialist.completed', { role, status: 'complete', output });
  return { role, output, ok: true };
} catch (e) {
  await deps.persist.updateSpecialist(id, { status: 'failed', errorMessage: String(e) });
  emit('specialist.completed', { role, status: 'failed' });
  return { role, ok: false };   // returns, never throws
}

Three decisions live in that block. The stream is a view; the database is the work — reload mid-briefing and D1 already holds exactly how far it got. Specialists are the cheap model (Sonnet, 2k tokens); we save Opus for the one call whose quality is most visible. A failed specialist returns a value, it doesn't throw — one death can't take down the other three or the synthesis.

Their prompts also carry the rule every model here obeys: do not perform arithmetic; cite only numbers already in the context. Figures are computed deterministically before the prompt exists. Models narrate numbers, they never produce them.

Phase 2a: the dependency stage

The fifth specialist reads the other four. After Phase 1 resolves, successful findings are collected and injected into the opportunities prompt, with unavailable substituted for anything that failed:

const phase1Findings = {};
for (const r of phase1Results) if (r.ok) phase1Findings[r.role] = r.output;
const anyPhase1Failed = phase1Results.some(r => !r.ok);

If tax died, opportunities simply has less to work with and says so, rather than inventing. This dependency staging is the actual reason for an orchestrator over a flat Promise.all.

Phase 2b: stream, and re-parse the tokens

Only the synthesizer (Opus) streams to the user. Anthropic returns its own SSE format; the browser wants ours. So the orchestrator sits in the middle, reads Anthropic's stream, and re-emits text deltas as synthesis.delta while accumulating the full document to persist.

The detail that matters is buffering. Network reads don't align to frame boundaries — one read() can hand you half a frame or two and a half. So accumulate, split on the \n\n delimiter, parse only complete frames, keep the remainder:

buf += dec.decode(value, { stream: true });
let idx;
while ((idx = buf.indexOf('\n\n')) !== -1) {
  const frame = buf.slice(0, idx); buf = buf.slice(idx + 2);
  const line = frame.split('\n').find(l => l.startsWith('data: '));
  const evt = JSON.parse(line.slice(6));
  if (evt.delta?.type === 'text_delta') { synthText += evt.delta.text; emit('synthesis.delta', { text: evt.delta.text }); }
}

Skip that step and it works locally, where chunks arrive whole, then drops tokens in production.

Partial failure is a status, not an exception

A briefing where one specialist failed but synthesis still shipped isn't "complete" and isn't "failed." It's complete_partial — a real value in the enum:

const status = anyPhase1Failed ? 'complete_partial' : 'complete';

The user gets a usable briefing with an honest marker that one section is thin. Synthesis is the one stage that can abort the whole run, since without it there's no document — specialist failures degrade, synthesis failure aborts. That asymmetry is deliberate. Below it, specialist calls retry with 1/2/4-second backoff, so most transient blips never surface as a failure at all.

The seam that makes it testable

The orchestrator never imports the Anthropic client or the database. It takes them as deps — runSpecialist, streamSynthesizer, persist. Production passes the real ones; tests pass fakes. That single indirection lets us test the entire fan-out/fan-in flow — parallelism, the dependency stage, partial-failure status, every emitted event — without spending a token or touching a database. Mock the tax role to fail, then assert the briefing ends complete_partial and the opportunities prompt got unavailable for tax. The model is non-deterministic; the orchestration around it is perfectly deterministic, as long as you keep the model behind a seam.

The takeaway

A multi-agent feature is mostly an orchestration and streaming problem; the model calls are the easy part. What earns trust is the rest: staging the dependency graph, persisting each step so the database is the source of truth, re-parsing one stream protocol into your own, naming partial failure as an outcome, and keeping the model behind an injected seam.

Get those right and six models can convincingly pretend to be one calm assistant thinking out loud.
